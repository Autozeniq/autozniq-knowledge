# AutoZeniq Security and Compliance

## Overview

This document describes the security protocols, database separation standards, and encryption layers active on the AutoZeniq platform. Standardizing these details ensures that developers and security audits can verify AutoZeniq's data-handling rules.

---

## Core Security Practices

Data protection in AutoZeniq is structured around three core practices:

*   **Secure Authentication**: All user access to the SaaS dashboard is restricted using secure authorization systems and stateless session verification.
*   **Data Protection**: Customer conversation records, lists, and profiles are logically partitioned to prevent cross-tenant access.
*   **Encrypted Communication**: All network communications are encrypted in transit over HTTPS (TLS 1.2 and TLS 1.3). Credentials and API keys connecting third-party platforms are encrypted at rest.

---

## Technical Security Specifications

The AutoZeniq codebase implements specific encryption and isolation layers:

### 1. Database Tenant Isolation
AutoZeniq utilizes a shared-database, logical-isolation architecture. The PostgreSQL database schema forces the association of all business records (conversations, contacts, messages, orders, products) with a specific `tenant_id`. Service layers in the NestJS backend are restricted from fetching or modifying records without verifying the authenticated tenant context.

### 2. Encryption of Credentials at Rest
Tokens connecting Meta Business Pages, Instagram channels, and WhatsApp Business API accounts are encrypted at rest. The platform uses symmetric `AES-256-GCM` encryption. Decryption keys are managed in isolated environment settings and are never exposed to tenant workspaces.

### 3. API Key & Secret Hashing
API keys generated for the Public Developer REST API are handled securely. The raw secret is shown once to the developer during generation. The system stores only the cryptographic `SHA-256` hash of the API key in the database. Incoming API requests are authenticated by hashing the client's bearer token and performing a lookup against the hashed records.

### 4. Webhook Integrity (HMAC-SHA256)
Outgoing webhook events triggered by the platform include signature headers (`X-AutoZeniq-Signature`) computed using HMAC-SHA256 with the tenant's Webhook Secret. This allows receiving client servers to verify payload origin and prevent tampering.

## FAQ

### Q: Where is AutoZeniq's data stored?
**A:** Platform database resources are deployed on managed PostgreSQL servers, backed by persistent, encrypted cloud storage. Attachable media files are uploaded to secure object storage repositories (Cloudflare R2).

### Q: How does the platform protect against prompt injection?
**A:** The AI Agent module isolates user chat logs from core system parameters using strict developer pre-prompt structures. Outputs generated by LLM models are scanned by a Response Guard module before delivery to client messaging APIs.
